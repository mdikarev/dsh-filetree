## doc-canon
For design and development, treat `docs/canon/` as the context source of truth. **Search first — it is mandatory when the index is available:** run `doc-canon search "<topic>"` (and `doc-canon code-index search` for covered-language code) before deep reads; on fail-closed (missing index) run `doc-canon index` / `code-index build` and retry; only if building fails, fall back to `docs/canon/INDEX.md` and note every read outside a pack (`doc_miss` / `code_miss`). Build a small working set, and expand if unsure before deep reads—without inventing structure. `docs/canon/future_plans/` holds directional initiatives for future system shape, not development tasks or checklists. For new or changed behavior, follow **canon-first**: update living canon via `canon-write` (do not edit `docs/canon/**` yourself) → optional project-local spec/plan if large → after substantial canon changes wait for user go-ahead → application code → close with `canon-audit`. Exceptions: pure bugfix with intended behavior unchanged, `code_stale`, non-behavioral edits. On docs↔code divergence, do not silently pick a side; use canon skills / `DISCREPANCIES.md`. During code analysis in a covered language, try `doc-canon code-index search` first; on empty/thin results, read source and note the miss (`code_miss`).
